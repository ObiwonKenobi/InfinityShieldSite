# Rolling 30 day threat brief: weekly procedure

This file is the instruction set for the Monday refresh of the rolling brief at
https://www.infinityshield.co/brief/. A scheduled Claude Code session reads it
and follows it. Edit this file to change how the brief is produced; the
schedule itself lives in the account's scheduled tasks, not in the repo.

The monthly archive (archive/) is a separate product with its own schedule and
is never edited by the weekly run.

## What the weekly run produces

- `brief/data/current.json` rewritten for the new 30 day window
- `brief/index.html` and the period and lede on `index.html`, both regenerated by
  `python3 tools/build_brief.py` (never hand edit these two files)
- a pull request against `main` for the owner to review and merge

Nothing is pushed to `main` directly.

## The window

The window is the 30 days ending on the Sunday before the run. For a run on
Monday 2 Nov 2026 the window is 3 Oct to 1 Nov 2026 and the period string is
`3 Oct – 1 Nov 2026` (digits, three letter month, en dash with spaces, year
once at the end, or on both dates when the window spans a year boundary:
`29 Dec 2026 – 27 Jan 2027`). `issued` is the run date in the same style,
`2 Nov 2026`.

## Procedure

1. Attach the repo with the `add_repo` tool (owner `ObiwonKenobi`, repo
   `InfinityShieldSite`, access `push`) if it is not already available, then
   clone it once with `git clone --depth 50` and a generous timeout. Do not
   clone twice in parallel. Work in a branch named `brief/YYYY-MM-DD` using the
   run date.
2. Read `brief/data/current.json`. It is the previous week's brief and your
   starting point. Read one or two files in `archive/data/` for voice and
   format. Read `tools/build_brief.py` for the validation rules.
3. Carry forward, then update. Drop every item whose main event or disclosure
   is now older than the window. Keep items still inside the window, and update
   their status where it changed (patch shipped, added to CISA KEV, victim
   count revised, arrest made). Then research the days that are new since last
   week, usually the last 7 to 9 days.
4. Research with WebSearch and WebFetch. Run 10 to 16 searches covering:
   critical and exploited vulnerabilities and zero-days (CISA KEV additions,
   vendor advisories, the Microsoft Patch Tuesday if one fell in the window),
   supply chain attacks (npm, PyPI, GitHub Actions, CI/CD, MSP and RMM tools),
   data breaches with record counts, ransomware and law enforcement actions,
   notable research disclosures, and certificate or internet-wide trust
   failures. Prefer primary sources: the vendor advisory, CISA, the regulator or
   court filing, the victim's own notice. Reputable security press is fine as a
   second source.
5. Write the new `brief/data/current.json`. Schema and limits are below.
6. Run `python3 tools/build_brief.py --check` and fix every problem it lists.
   Then run `python3 tools/build_brief.py` with no flag. It writes
   `brief/index.html` and updates `index.html`.
7. Confirm the only changed files are `brief/data/current.json`,
   `brief/index.html`, and `index.html`. Confirm `grep -c "—" brief/ index.html`
   reports zero em dashes.
8. Commit on the branch and push it with `git push -u origin brief/YYYY-MM-DD`.
   Open a pull request against `main` titled
   `Rolling threat brief: <period>`. The body must list: items added, items
   dropped, items whose status changed, everything in `unverified`, and any
   weak spots or single-source claims the owner should look at before merging.
9. Finish with a short summary for the owner that repeats the PR link.

## Rules

- Never invent a CVE number, a record count, a date, a victim name, or a URL.
  Every URL in `sources` must come from your own search or fetch results.
- Where sources conflict, say so in the text and give both figures.
- A claim from a single weak source goes in `unverified`, not in the tables.
- If something cannot be verified, leave it out. A shorter brief is fine.
- Dry and factual. Short paragraphs, plain numbers, no adjectives doing the
  work of facts, no marketing language, no exclamation marks.
- No em dashes anywhere. Use a comma, a colon, or a full stop. En dashes are
  only for the date range in `period`.
- Dates inside text are `20 Oct`, with the year only when it is not the
  current year.
- Do not edit `archive/`, `about.html`, `brief.css`, or anything under `tools/`.
- Do not include a model name in the commit message, the PR title, or the PR
  body.

## Schema for brief/data/current.json

```json
{
  "period":   "29 Sep – 28 Oct 2026",
  "issued":   "28 Oct 2026",
  "lede":     "Two sentences at most. What defined the window.",
  "top": [
    {
      "title":  "Short headline",
      "sev":    "crit | high | med",
      "status": "Critical · exploited",
      "body":   "One paragraph. What happened, who reported it, what is confirmed, where sources disagree.",
      "facts":  [["CVE", "CVE-2026-00000"], ["CVSS", "9.8"], ["Fixed in", "1.2.3"]],
      "action": "Imperative. What a defender should do this week."
    }
  ],
  "vulns": [
    {"product": "Vendor Product", "cve": "CVE-2026-00000", "allows": "What an attacker gets", "sev": "crit", "status": "Exploited", "note": "KEV 20 Oct. Fixed in 1.2.3."}
  ],
  "supply":   [{"label": "Package or service, date", "text": "One paragraph."}],
  "breaches": [{"org": "Organization", "scale": "4.2M records", "cause": "How, when, what data."}],
  "unverified": "Claims only weak sources report, or an empty string.",
  "other":    [{"label": "Event, date", "text": "One paragraph."}],
  "todo":     ["Imperative sentence.", "Another."],
  "sources":  [{"title": "Publisher: headline", "url": "https://..."}]
}
```

Limits enforced by `build_brief.py --check`: `top` exactly 3; `vulns` 6 to 14;
`supply` 1 to 6; `breaches` 6 to 15; `other` 1 to 6; `todo` 5 to 10; `sources`
10 to 40. `facts` and `note` are optional. `sev` must be `crit`, `high`, or
`med`.
